# Release

Use only for an explicitly authorized release. Reuse existing authorization; a green gate alone never authorizes publication. A deploy-only request follows [README deployment](../../../README.md#deployment) without creating a tag.

1. **Inspect state**: check `main`, upstream, staged and unstaged changes, accounts, and local/remote tags. Include only reviewed work; never move an existing release tag.
1. **Reconcile infrastructure**: apply any infrastructure changes through the [infra skill](../infra/SKILL.md) before application rollout.
1. **Run local gates**: run `mise run all` and `mise run check:links`, resolving failures and reviewing warnings without suppressing them. Add browser/Lighthouse qualification appropriate to the changed pages.
1. **Commit and derive version**: commit reviewed implementation paths with Conventional Commits. Use the owner's requested version; otherwise derive the next semver with the pinned `mise exec -- git-cliff --config ~/.config/git-cliff/cliff.toml --unreleased --bumped-version`.
1. **Update release metadata**: set the version in `pyproject.toml`, `uv.lock`, and `server.json` (`uv version <version>` updates the first two). Prepend `CHANGELOG.md` once with `mise exec -- git-cliff --config ~/.config/git-cliff/cliff.toml --unreleased --tag v<version> --prepend CHANGELOG.md` (replace the section on retry; use the UTC publication date and keep earlier notes intact).
1. **Push and watch CI**: run `mise run all` on the final release candidate, inspect the diff, commit the release metadata as `chore(release): vX.Y.Z`, and push `main`. Watch every `main` push through promotion (`gh run list --workflow deploy.yml --commit <sha>` and `gh run watch <run-id> --exit-status`): when tool setup fails on GitHub download errors (HTTP 5xx), wait until downloads respond, then `gh run rerun <run-id> --failed`. A run superseded by a newer `main` commit skips its deploy, and a re-run of it fails the deploy job's head check, so watch the newest commit's run.
1. **Review logs**: the green deploy run already smoke-tested the image (pages, stylesheet, MCP 405 on GET/HEAD, an MCP client session) and ran the `test:deployed` checks on the promoted revision (ready revision, 100% traffic, digest, commit, public `/health`, `/api/profile`, MCP server card and initialize). Review recent error logs separately with the owner identity; the deployer has no log-reading role.
1. **Qualify live production**: verify what the pipeline does not probe: apex DNS, the TLS certificate, the apex redirect, `/agents`, `/llms.txt`, sitemap, feed, and archive indexes; correlate any truncation warnings with the serving revision and request method instead of dismissing a 200 status. Run `gh workflow run quality.yml -f target=production` against the qualified ref and require its browser/Lighthouse results ([README](../../../README.md#tasks) lists local equivalents and score rules; prefer clean runners when workstation contention distorts scores). A red quality run blocks tagging: fix and requalify on a new commit, retaining failed reports.
1. **Tag and publish GitHub release**: create an annotated tag at the qualified commit and push it without force. Publish with `gh release create ... --verify-tag --notes-file <temporary-file>`, verify the remote tag and release target, and remove the temporary notes file.
1. **Publish to MCP Registry**: install the pinned publisher once with `mise install --locked github:modelcontextprotocol/registry`, validate with `mise exec -- mcp-publisher validate server.json`, log in via `MCP_GITHUB_TOKEN="$(gh auth token)" mise exec -- mcp-publisher login github` with the `fmind` account active in `gh` (owns `io.github.fmind`), and run `mise exec -- mcp-publisher publish server.json`; never pass the GitHub token as an argument or edit the publisher's token file. Verify the published version is the [latest](https://registry.modelcontextprotocol.io/v0.1/servers/io.github.fmind%2Fportfolio/versions/latest) active entry and the skill index digest matches the served Markdown. Release authorization includes this channel unless the owner narrows scope.

CI does not roll back after promotion: if `test:deployed` or live verification fails, roll back first with `mise run deploy <digest-ref> <commit-sha>` using the preceding qualified digest and commit, then run `test:deployed` with the same pair. If an advisory published since that digest shipped blocks its scan, route traffic back to the preceding ready revision with `gcloud run services update-traffic www-fmind-dev --project www-fmind-dev --region europe-west1 --to-revisions <revision>=100`, then fix forward with a patched release. A release is complete only after local archive proof, exact-commit CI, live runtime, GitHub release, and MCP Registry publication are all verified.
